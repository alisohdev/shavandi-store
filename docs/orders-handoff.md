# Order creation and reservations

Signed-in customers can review the account cart and create a temporary order reservation. The amount is the merchandise subtotal only. No shipping fee, recipient details, payment, fulfillment or paid-order transition is introduced. Reservations last 15 minutes, and each account can hold one active reservation. Customers see their latest 20 orders at /orders/ and can cancel their own pending reservation.

API: GET /api/v1/orders lists the session owner's recent orders. POST /api/v1/orders accepts only {key, quote_token}; key is a client-generated UUID, and quote_token comes from the cart response. POST /api/v1/orders/{id}/cancel accepts {}. All writes require existing Origin/CSRF/session guards. The caller cannot submit a user ID, prices, order lines or status.

The cart quote token hashes its server-resolved lines, including current quantities, prices, visibility and stock availability. Order creation recalculates that quote inside its transaction. Any change requires a new cart review. An account-scoped request key returns the same original order on replay, including after cancellation/expiry; it never reserves twice. A reused key with a different quote returns 409. The browser retains its request key across retries in the current page. If the page is lost after an uncertain request, visit /orders/ before creating another; the one-pending-order constraint prevents a second active reservation.

Migration 20261110140000 adds orders/order_lines and variants.reserved_quantity. Physical stock is unchanged by reservations; public/cart availability is stock_on_hand minus reserved_quantity. Reservations and releases advance stock_version. Admin physical-count updates cannot reduce stock below reservations. Ordinary catalog edits preserve reservations. The same catalog transaction lock serializes order creation, release and catalog/inventory mutations. Per-customer locks also serialize cart clearing with cart writes. This is intentionally conservative for this store's current scale.

Creation stores immutable names/options/quantity/unit-price snapshots, reserves all lines and clears the cart in one transaction. Failure rolls everything back. Cancellation and expiry release only pending orders and update state in the same transaction. Expiry runs on API startup and once per minute with a bounded context, and before order operations, in batches of 100. It catches up after restarts; a large backlog can temporarily reduce availability until later batches complete. Running multiple API processes is safe through the shared database lock. Expiry never increases physical stock.

Tests cover two customers racing for one item, request replay, owner isolation, stale quotes, immutable prices, injected order-line failure rollback, duplicate cancellation/expiry, replay after expiry, and preventing counts below reserved stock. Browser tests exercise uncertain-network retries using the same key, creation, order review, cancellation, sign-in and mobile overflow against API fixtures. Database tests provide the persistence/concurrency evidence; a provisioned browser-to-real-auth walkthrough remains separate.

Apply the migration through the existing Goose workflow before starting this API version. Tests migrate only the isolated _test database. No development/production migration, payment, message delivery or deployment was performed. Shipping/checkout rules and the payment provider are prerequisites for the next commerce phase.
