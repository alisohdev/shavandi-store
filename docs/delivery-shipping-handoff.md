# Delivery details and merchant shipping rates

The store owner defines shipping methods in admin: name, flat fee in integer toman, and active status. No rate is seeded. Zero means an explicitly configured free method. There are at most 50 methods, each with a rate from zero through one billion toman. Rates are per order, not per item. This slice has no postcode-zone, weight, carrier or province-dependent calculation; the owner names the methods and controls their fees. Deactivate a method to stop new selections; existing saved snapshots remain intact.

Public GET /api/v1/shipping-methods lists active methods. Admin GET/POST /api/v1/admin/shipping-methods list all and save a versioned method; creation uses an empty id and version zero. Editing requires its current version. MFA administrator authorization, exact Origin and signed CSRF apply. No hard delete API is provided.

Customers enter recipient name, Iranian mobile, province, city, street address and ten-digit postcode on their active reservation at /orders/. POST /api/v1/orders/{id}/delivery saves those fields plus the delivery version, shipping_method_id and shipping_version. Version zero creates the first details record. Phone and postcode accept Persian/Arabic digits and normalize server-side. Text fields have explicit limits. All writes derive ownership from the authenticated session. Details cannot be changed after cancellation or expiry and never extend the reservation deadline.

The server rechecks the active method/version and snapshots its name and fee with the delivery record. It rejects caller-supplied fees. A rate change before saving returns a conflict requiring refreshed review; later edits to the method do not change an already saved fee. The order screen displays merchandise subtotal, shipping and their sum. When no method is active, an address can be saved without a shipping quote, but no zero fee or payable total is inferred. If any method is active, selecting one is required. Prices remain bounded for exact browser arithmetic.

Delivery updates use optimistic version checks so another tab cannot silently overwrite details. A conflict preserves current form input and offers manual order refresh; refreshing replaces unsaved input. Order auto-refresh was removed to avoid discarding address drafts. After an uncertain delivery response, refresh to inspect the saved version. Shipping methods must also be refreshed if their rate changed. The reservation expiry worker remains authoritative.

Migrations 20261110150000 and 20261110160000 add order delivery details and shipping configuration. Apply through the existing Goose workflow before running the updated API. Automated tests migrate only the isolated _test database. Addresses are stored in PostgreSQL and returned only through the owner's authenticated order endpoints, with no-store responses. The app does not put address data into local/session storage, URLs or logs. This phase does not introduce a retention/deletion job; define retention before production launch.

Zarinpal is the user-selected payment provider for the next phase. Payment initiation, gateway callbacks, verification, paid-state transitions and fulfillment remain unimplemented and disabled. The shipping-inclusive total is a review amount, not a charge. Existing temporary reservations still last fifteen minutes.

Verification covers delivery normalization/validation, owner isolation, persisted details, concurrent edits, stale delivery/shipping versions, unchanged reservation deadlines, inactive methods, rate snapshots and rejected caller-supplied fees. Browser tests use API fixtures for merchant rate management, method selection, displayed totals, address refresh/conflicts, mobile layout and absence of personal details in browser storage. These do not replace a real-account browser-to-database walkthrough.
